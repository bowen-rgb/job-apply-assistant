# 参考覆盖核验

在用户给出参考仓库、要求吸收整套经验或质疑完成度时读取。普通单组件微调沿用主文件即可。

## 1. 固定输入范围

记录仓库 URL、提交、当前文件清单；核对文件是否在本地，区分浅克隆与完整历史。把用户图片、文字、链接分别登记，缺失的临时附件如实标记。扫描 README、导出入口、实际示例与设计文档索引，按当前文件确定模块数，不能只抄作者计数。

涉及 Caho1/open-claude-ui 时读取 [该参考的核验提示](open-claude-ui.md)，然后检查当前版本；提示只代表固定提交，不替代实际源码。

完成条件：素材列表、版本和模块清单可查。下载不是阅读；浏览接口/事件不是逐行精读；作者自称官方或生产级不是独立验证。

## 2. 以目标场景建立逐项表

每行使用：参考模块/原则｜源码位置与实际行为｜本项目场景｜状态｜本地实现入口｜验证或限制。多个项目分别填写，A 项目的实现不算 B 项目已采用。

状态只表达真实含义：

- **已借鉴**：参考确实改变了实现；指出采用差异，不能只凭相似就归因。
- **原有能力**：参考之前已存在；核验后保持，不能当作新增成果。
- **部分采用**：列出采用的子能力和缺少的子能力。
- **待增强**：场景存在，但该体验未实现或尚未完成验证。
- **不适用**：说明缺少什么业务场景，或为何现有架构不需要它。

不适用示例：无录音场景，不增加麦克风波形。待增强示例：已有图片查看器，尚无缩略图共享转场。参考样例包含多个子功能时允许一行多个状态。只数行数会掩盖子能力缺失，因此交付时优先列有价值的缺口。

## 3. 核对冲突与实现

对采用项和有用缺口，读事件处理、状态变更、边界与清理逻辑。注释宣称阈值/焦点陷阱/后台通道时，找到实际执行路径；未找到就保留为未证实。检查参数的单位、公式、命名和数值推导是否一致。参考实现有缺陷时修正适配方案，保留许可和固定源链接。

分别处理视觉与行为：保留品牌不等于拒绝交互改善；引入弹簧不代表每个动作都需要弹跳。涉及自动重试时区分读取与写入，写操作需要业务幂等与权限，不能将 UI 重试示例视为可靠性保证。

完成条件：有用缺口得到本次补齐或明确的待增强状态；选择有业务理由；承认未做项。

## 4. 验收与回写

将采用项映射到用户可观察的断言。例：锚点缩放检查光标下图像点；渐隐检查上下边界与键盘焦点；分组导航检查从第一项反向回绕；输入法检查合成中后台刷新也不误触发。

完成一批桌面/手机、减少动效、键盘、长文本与错误场景检查；集中修复后最多确认一批。记录失败原因和实际通过范围。复查项目构建脚本副作用，隔离预览不得覆盖发布产物或用户数据。

交付区分：本次新增、已有且验证、待增强、无场景；给出核验表与预览。更新 skill 的规则时验证引用存在、格式有效，并用本次真实项目缺口检验规则能否促使下一次发现，而不是用关键词命中率冒充行为评估。
