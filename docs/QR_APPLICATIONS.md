# 二维码投递

菜单 **二维码投递** → 上传 HR 给的二维码图片 → 确认企业及拟用简历 → **一键投递**。

上传只识别，不发送申请。图片在本机识别，不调用外部图片识别服务。支持 PNG、JPG、WebP、BMP，最大 8 MB、2000 万像素。照片里有多个二维码时先选申请入口；已有网址也可直接输入。

## 简历怎样选择

- 有具体岗位：优先按岗位内容和档案中的简历标签推荐。
- 通用收简历页：有明确机械、机器人/控制、数字化主题时，可推荐相应方向，明确标为根据页面推测；无足够依据则推荐综合版。
- 科研类企业可能涉及多个技术方向，不仅凭“科研”二字替你选定专业。
- 企业名称来自 JobPosting 或网页站点名称；无法识别时要求补充。企业类型是关键词推测，并提供依据，不声称已验证企业身份。
- 可在窗口中换选 CV。这个选择只针对本次申请，不修改全局默认简历。

## 点击以后

本次点击授权当前档案、目标页面和所选简历。如果档案已启用动机信，系统通过当前 LM 规则起草和复核信件，再交给已有平台工作进程填写表单并尝试发送。记录为**单次自动材料授权**，不伪称用户已逐字阅读生成的信件。

专用 Chrome 必须可连接。缺失时窗口显示错误和打开 Chrome 按钮。登录、验证码、隐私条款、必填问题或网站不兼容会转为需要用户处理。可接管 Chrome、打开接收方网址、停止任务或继续本次申请；如果页面已关闭，可先通过目标链接重新打开。不会切换到 Edge。

结果必须以网站确认及已有持久回执为准。不确定发送结果时不重复点击发送。已开始请求不会因重复点击再次启动；资料、简历或岗位发生变化时授权失效，需要重新识别和确认。

原有队列和全局自动启动/自动提交选项不受影响。每个候选人的 QR 请求、材料和申请记录分别保存。

## UI 参考与验证

采用用户指定 Refactoring UI 的规则，结合现有原生 HTML/JS/CSS 及样式变量：

| 规则 | 实际应用 | 验证 |
| --- | --- | --- |
| §2.8 操作层级 | 每个状态保留一个主操作，证据和链接为次级内容 | 桌面及手机截图 |
| §3.6 分组间距 | 企业、简历、授权说明分组；组间距大于组内距 | 桌面及手机截图 |
| §3.4.2 窗口宽度 | 固定最大宽度，窄屏单列，内部可滚动 | 1280、375 像素，无横向溢出 |
| §5.7 非颜色信号 | 明确文字说明识别中、待登录、失败和已确认 | 界面交互测试 |
| §8.4 空状态 | 给拍照示例和唯一上传入口；识别后才显示投递操作 | 空状态截图与无自动发送断言 |

界面截图使用模拟企业和测试二维码：[桌面](assets/qr-application-desktop.png)、[手机](assets/qr-application-mobile.png)。

测试包括真实二维码图片解码、多个码、损坏图片、手机专用码、内网链接、过期页、简历路由、跨档案隔离、重复启动、资料变化、LM 检查失败拦截；模拟网页中调用平台 apply_worker 上传、提交一次并保存回执，确认旧队列未改变。

这些测试不证明任何真实 HR 页面都能投递。微信专属二维码需要手机处理，未知/过期链接、动态登录或站点限制可能需要接管。本轮没有真实 HR 二维码的外部投递验收，也没有向真实招聘方发送测试材料。
