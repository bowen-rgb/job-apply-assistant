# 申请材料审核与提交凭证

这批优化借鉴 [Useless-LinkedIn](https://github.com/ziyuan-404/Useless-LinkedIn) 的材料版本和提交证据思路，沿用本项目的网页控制台、多候选人隔离和六语界面。实现为本项目独立编写。

## 如何使用

1. 完成岗位评估和人工确认，运行申请准备流程。
2. 在岗位卡片或申请队列中点击“审核申请材料”。打开实际使用的简历、求职信及合并文件，核对岗位信息；需要时展开表单使用的求职信正文。
3. 勾选已检查，再点击“批准这些版本”。批准本身不会发送申请。
4. 默认继续由你在招聘网站检查并手动发送。如果已经开启自动发送，明确重新运行准备流程后，系统才会尝试使用批准版本发送。自动队列启动和自动发送是两个独立设置。

文件、求职信正文、岗位内容、评估版本、简历选择或保存的个人资料变化后，批准失效。请重新准备和审核。合并 PDF 在输入文件不变且缓存完整时直接复用，避免重跑时悄悄替换已审核的字节。

## 状态分别表示什么

| 页面状态 | 含义 |
| --- | --- |
| 已发送 | 用户确认已经发送，不表示系统观察到了招聘网站的回执 |
| 网站已确认提交 | 自动发送后观察到成功确认文字，并保存了可检查完整性的本地凭证 |
| 已发送 · 凭证待核验 | 旧记录没有本批机制的凭证，或现有凭证缺失、被修改；需要人工核对 |
| 结果待核对 | 已开始一次发送，但没有确认结果；先检查招聘网站，再手动处理 |

普通状态接口不能写入“网站已确认提交”。发送前会先保存尝试记录；超时、关闭程序、重跑准备或改变页面状态都不会让系统自动再次点击发送。已发送、撤回和招聘方回复不会被迟到的准备任务覆盖。

## 凭证范围和存储

凭证包含岗位、发送尝试、批准版本、确认文字、网址和观察时间。文件摘要与数据库记录用于发现本地凭证的缺失或变更。它证明浏览器观察到了什么，不能保证招聘方邮箱收件、网站后台最终入库或申请结果。

材料版本、准备审计和提交凭证保存在当前候选人自己的数据目录；批准和发送尝试在对应数据库中。文件下载只接受系统记录的材料角色，不接受任意路径。这些文件可能包含个人信息，均不提交 Git。

## 本批边界

本批完成材料批准、批准失效、提交凭证和防重复发送。可追溯职业事实库、逐条声明与原文关联、岗位扫描断点恢复仍属于后续工作。本批没有宣称能够自动证明经历真实性，也没有用真实岗位进行投递测试。
